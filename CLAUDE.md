# Daily Fitness

Веб-приложение для планирования и учёта силовых тренировок. Пользователь регистрируется, планирует тренировки на неделю, собирает каждую тренировку из упражнений (из готового каталога или своих) и задаёт для каждого упражнения подходы, повторения и рабочий вес.

Проект учебный: автор — фронтенд-разработчик. Цель — пройти полный продакшн-цикл самому: бэкенд, БД, Docker, nginx, деплой на свой VPS.

## Как работать с Claude в этом проекте

- **Большую часть кода автор пишет сам.** Не пиши и не правь код, пока об этом явно не попросили. На вопрос «как сделать X» сначала объясни подход и дай направление, а готовую реализацию — только по запросу.
- **Бэкенд, БД и DevOps объясняй подробнее.** Автор сильный во фронтенде, но новичок в бэкенде. Если предлагаешь бэкенд- или инфраструктурное решение, кратко поясни *почему* так (безопасность, производительность, принятая практика). Азы React объяснять не нужно.
- Когда пишешь код по просьбе, держись стиля и структуры, которые уже есть в репозитории, а не вводи свои паттерны.
- Отвечай на русском. Код, идентификаторы и комментарии в коде — на английском.

## Объём MVP

1. **Регистрация и вход**: email и пароль, выход, восстановление сессии после перезагрузки страницы.
2. **Каталог упражнений**:
   - заранее подготовленный глобальный список (seed), у каждого упражнения есть название, группа мышц, тип снаряда (штанга, гантели, тренажёр, собственный вес…) и флаг «учитывается ли вес»;
   - пользователь может создать своё упражнение с любым названием. Оно видно только ему.
3. **Недельный план**:
   - просмотр недели (пн–вс) и переключение на предыдущую/следующую;
   - на любой день можно добавить одну или несколько тренировок;
   - в тренировке упорядоченный список упражнений.
4. **Подходы**: у каждого упражнения в тренировке список подходов. У каждого подхода своё число повторений и свой вес (кг), если упражнение предполагает вес. Подходы могут отличаться друг от друга (например, пирамида 60×10, 70×8, 80×6).

**Не входит в MVP** (на потом): отметка «выполнено» и фактические результаты против плана, шаблоны и копирование недели, прогресс и графики, таймер отдыха, PWA/офлайн, соцлогин, восстановление пароля по email.

## Стек

### Фронтенд (`apps/web`)
- React + TypeScript, Vite
- TanStack Query (react-query) для всего серверного состояния (данные API)
- Zustand только для клиентского состояния: access-токен, текущий пользователь, выбранная неделя, UI-состояние. Серверные данные в Zustand не дублировать.
- CSS Modules
- React Router
- Формы: react-hook-form + `@hookform/resolvers/zod` со схемами из `packages/shared`
- UI **mobile-first**: основной сценарий — телефон в зале. Язык интерфейса — русский, без i18n.

### Бэкенд (`apps/api`)
- Node.js (актуальная LTS) + TypeScript
- **Fastify**, валидация запросов и ответов через **Zod** (`fastify-type-provider-zod`)
- PostgreSQL + **Prisma ORM** (схема, миграции, seed)
- Аутентификация: JWT access + refresh (подробности ниже), хеширование паролей через `argon2`
- Плагины: `@fastify/cookie`, `@fastify/cors` (только для dev), `@fastify/helmet`, `@fastify/rate-limit` (на эндпоинты auth)
- Логирование: pino (встроен в Fastify)

### Общее (`packages/shared`)
- Zod-схемы и выведенные из них TS-типы для DTO (запросы и ответы API). Используются и в API, и на фронте. Это единый источник правды для контракта.

### Инструменты
- pnpm workspaces (монорепо)
- Oxlint (один конфиг в корне на всё монорепо, type-aware правила через tsgolint) + Prettier
- Vitest для юнит-тестов; для интеграционных тестов API — `fastify.inject()` на тестовой БД

## Модель данных (черновик)

```
User            id, email (unique), passwordHash, createdAt
RefreshToken    id, userId, tokenHash, expiresAt, revokedAt, createdAt
Exercise        id, name, muscleGroup?, equipment?, tracksWeight (bool),
                ownerId? (null = глобальное из каталога, иначе — кастомное пользователя)
Workout         id, userId, date (@db.Date), title?, notes?, order, createdAt
WorkoutExercise id, workoutId, exerciseId, order, notes?
WorkoutSet      id, workoutExerciseId, order, reps (int), weightKg (Decimal?, null если без веса)
```

Решения:
- Кастомное упражнение — это запись `Exercise` с `ownerId = userId`, а не свободный текст в тренировке. Так его можно переиспользовать и позже строить статистику.
- Каталог для пользователя = `ownerId IS NULL OR ownerId = currentUser`.
- `date` хранится как `DATE` без времени, чтобы не было проблем с часовыми поясами. «Неделя» не отдельная сущность, а диапазон дат пн–вс, который считает фронт.
- Вес в кг, `Decimal(6,2)`: блины бывают по 1.25 кг, float для этого не годится.
- Все связи от `Workout` вниз удаляются каскадно.
- **Каждый запрос к данным фильтруется по `userId` из токена.** Чужие ресурсы должны отдавать 404.

## API (черновик)

Все роуты под префиксом `/api`.

```
POST   /auth/register
POST   /auth/login
POST   /auth/refresh              # по refresh cookie → новый access (+ ротация refresh)
POST   /auth/logout
GET    /me

GET    /exercises                 # глобальные + свои, ?search=&muscleGroup=
POST   /exercises                 # создать кастомное
PATCH  /exercises/:id             # только свои
DELETE /exercises/:id             # только свои

GET    /workouts?from=YYYY-MM-DD&to=YYYY-MM-DD   # тренировки недели со вложенными упражнениями и подходами
POST   /workouts
GET    /workouts/:id
PATCH  /workouts/:id
DELETE /workouts/:id
PUT    /workouts/:id/exercises    # целиком заменить упражнения и подходы тренировки (в транзакции)
```

`PUT` для содержимого тренировки выбран сознательно: форма тренировки на фронте редактируется целиком, и отправлять всё дерево одним запросом в транзакции проще и надёжнее, чем десятки мелких CRUD-запросов на подходы.

Ошибки возвращаются в едином формате: `{ error: { code: string, message: string, details?: unknown } }`.

## Аутентификация (JWT access + refresh)

- **Access-токен**: JWT живёт ~15 минут и хранится **только в памяти** (Zustand), не в localStorage. Передаётся в `Authorization: Bearer ...`.
- **Refresh-токен**: случайная строка (не JWT) живёт ~30 дней и хранится в cookie `httpOnly; Secure; SameSite=Strict; Path=/api/auth`. В БД лежит только её хеш.
- **Ротация**: при каждом `/auth/refresh` старый refresh отзывается и выдаётся новый. Если приходит уже отозванный токен, это признак кражи: отзываются все refresh-токены пользователя.
- **Фронт**: при старте приложения вызывает `/auth/refresh`, чтобы восстановить сессию. Fetch-клиент на `401` один раз пробует refresh и повторяет запрос. Параллельные запросы должны ждать один общий refresh, а не запускать свой каждый.
- Секреты (`JWT_SECRET` и т.п.) берутся из env и валидируются через zod при старте.
- На `/auth/login` и `/auth/register` действует rate-limit.

## Локальная разработка

- Postgres поднимается через `docker compose up -d`. API и web запускаются локально через `pnpm dev`.
- Vite проксирует `/api` → `http://localhost:<api-port>`, чтобы фронт и API были на одном origin, как в проде (cookie работают без CORS-плясок).
- `.env.example` лежит в каждом приложении, реальные `.env` в git не попадают.
- Миграции: `prisma migrate dev`. Seed каталога: `prisma db seed`.

> Команды (`pnpm dev`, `pnpm build`, `pnpm lint`, `pnpm test` и т.д.) нужно дописать сюда, когда они появятся в `package.json`.

## Продакшн и деплой

Цель — самостоятельный хостинг на VPS:

- **docker-compose.prod.yml**: `postgres` (volume для данных, наружу не публикуется), `api` (multi-stage Dockerfile, запускается от non-root пользователя), `nginx`.
- **nginx**: раздаёт собранную статику `apps/web` (SPA fallback на `index.html`, долгий кеш для хешированных ассетов) и проксирует `/api` → `api`. Фронт и API живут на одном домене.
- **HTTPS**: Let's Encrypt (certbot), редирект с HTTP на HTTPS, HSTS.
- **Миграции** на проде: `prisma migrate deploy` при деплое, до старта нового API.
- **Бэкапы**: `pg_dump` по крону с ротацией; хранить копию вне VPS.
- **Сервер**: SSH только по ключу, firewall (ufw) с открытыми только 22/80/443.
- Позже: CI/CD через GitHub Actions (линт, тесты, сборка образов, деплой по SSH), healthcheck-эндпоинт `/api/health`.

### Токены в коде
- Токены живут в `apps/web/src/styles/tokens.css` как CSS-переменные (`--bg`, `--surface`, `--accent`, `--radius-card`, `--space-16`…). Значения берутся из `tokens.json` дизайн-системы.
- В `*.module.css` используются только `var(--…)`: никаких hex, rgb и «магических» радиусов. Новый цвет или размер сначала добавляется в дизайн-систему.

### UI-компоненты
Названия и props совпадают с макетом: `Button` (variant: primary | outline | add | slot), `TopBar` (variant: back | close | back-icon), `DayHeader`, `WorkoutCard`, `ExerciseCard`, `ExerciseListItem`, `SetRow`, `Chip`. Базовые компоненты лежат в `components/`, доменные — в соответствующей `features/*`.

### Правила интерфейса
- Подход записывается как `60 × 10` (кг без единицы), без веса — `12 повт.`; дробный вес через запятую.
- Обращение на «ты», кнопки — инфинитив («Добавить подход»).
- Нажимаемые элементы не меньше 44px; одна `primary`-кнопка на экран.
- Фокус: кольцо 2px `accent`; `outline: none` без замены запрещён.

## Соглашения

- TypeScript `strict`, без `any` (при необходимости используй `unknown` и сужение типа).
- Контракт API описывается только в `packages/shared`. Если меняется ответ API, сначала меняется схема там.
- Query keys в react-query задаются через фабрики, например `workoutKeys.week(from, to)`. После мутаций инвалидируются соответствующие ключи.
- Имена файлов: компоненты в `PascalCase.tsx`, стили рядом в `Component.module.css`, остальное в `kebab-case.ts`.
- Язык UI-текстов — русский, пишутся прямо в компонентах.
