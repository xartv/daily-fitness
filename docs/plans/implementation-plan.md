# План реализации Daily Fitness

Верхнеуровневый поэтапный план реализации MVP из `CLAUDE.md`.

## Принципы

- **Деплоить рано.** Голый скелет «фронт + API + БД» выкатывается на VPS сразу, как только заработал локально. Проблемы с Docker, nginx, cookie и HTTPS проще разбирать, пока кода мало. Дальше каждая фича сразу доезжает до прода, и продакшн-цикл проходится много раз, а не один раз в конце.
- **Схема БД уже спроектирована** в `CLAUDE.md`, поэтому отдельным этапом её делать не нужно. В код она попадает на этапе 2.
- **Ритм внутри фичевых этапов (5–8):** схема в `packages/shared` → сервис и роут → тесты API → UI → деплой. Контракт всегда появляется первым, и фронт с бэком не расходятся.

---

## Этап 0. Фундамент монорепо

- [ ] `git init`, `.gitignore` (`node_modules`, `.env`, `dist`)
- [ ] pnpm workspaces: `apps/web`, `apps/api`, `packages/shared`
- [ ] Общий `tsconfig.base.json` со `strict`, ESLint и Prettier на всё монорепо
- [ ] Пустой `packages/shared` с `zod`; проверить, что пакет импортируется из обоих приложений

**Готово, когда:** `pnpm lint` и `pnpm build` проходят по всем пакетам, а команды записаны в `CLAUDE.md`.

## Этап 1. Скелет API и база

- [ ] `docker-compose.yml` с Postgres (volume, порт только на localhost)
- [ ] Fastify и `server.ts`, конфиг env через zod. Если переменной нет, приложение падает сразу при старте, а не посреди запроса.
- [ ] Плагины: глобальный error handler в формате `{ error: { code, message } }`, helmet, pino
- [ ] `GET /api/health`
- [ ] Prisma: `prisma init` и плагин, который декорирует `fastify.prisma`

**Готово, когда:** `pnpm dev` поднимает API, `/api/health` отвечает 200, Prisma подключается к БД.

## Этап 2. Схема данных и seed

- [ ] Перенести модели из черновика в `schema.prisma`: связи, `onDelete: Cascade`, `@db.Date`, `Decimal(6,2)`, индексы (`Workout(userId, date)`, `Exercise(ownerId)`)
- [ ] Первая миграция `prisma migrate dev`
- [ ] `seed.ts` с глобальным каталогом упражнений (`ownerId = null`)

Модель небольшая и уже продумана, поэтому лучше сделать её целиком сразу, чем раздувать миграциями по ходу. Индекс по `(userId, date)` нужен потому, что главный запрос приложения — «тренировки пользователя за неделю».

## Этап 3. Скелет фронта

- [ ] Vite + React + TS, прокси `/api` на API
- [ ] React Router, провайдер QueryClient, пустой Zustand-стор
- [ ] `tokens.css` из дизайн-системы, шрифт Onest, базовые компоненты (`Button`, `TopBar`, `Chip`)
- [ ] Временная страница, которая дёргает `/api/health`: так видно, что прокси работает

## Этап 4. Ранний деплой (walking skeleton)

- [ ] Multi-stage Dockerfile для API (non-root), сборка web в статику
- [ ] nginx: статика, SPA fallback, проксирование `/api`
- [ ] `docker-compose.prod.yml`: Postgres наружу не публикуется
- [ ] VPS: SSH только по ключу, ufw (22/80/443), домен, certbot, редирект на HTTPS, HSTS
- [ ] `prisma migrate deploy` перед стартом API

**Готово, когда:** по `https://<домен>` открывается фронт, который получает ответ от `/api/health` из прода.

## Этап 5. Аутентификация (сквозная)

Самый сложный и важный этап. Делать в таком порядке:

1. [ ] `shared`: схемы `RegisterInput`, `LoginInput`, `UserDto`
2. [ ] API: argon2, register/login, выдача access JWT и refresh cookie, хеш refresh в БД, `/auth/refresh` с ротацией и детектом повторного использования, logout, декоратор `authenticate`, `GET /me`, rate-limit
3. [ ] Интеграционные тесты через `fastify.inject()`. Здесь они окупаются сильнее всего: ротация и отзыв токенов легко ломаются незаметно.
4. [ ] Фронт: стор токена, fetch-клиент с одним общим refresh на 401, восстановление сессии при старте, защищённые роуты, формы входа и регистрации
5. [ ] Деплой и проверка cookie (`Secure`, `SameSite`) уже на HTTPS

## Этап 6. Каталог упражнений

- [ ] `shared`: схемы упражнения и фильтров
- [ ] API: `GET` (глобальные + свои, поиск, фильтр), `POST`/`PATCH`/`DELETE` только для своих, чужое отдаёт 404
- [ ] Фронт: список с поиском и чипами групп мышц, создание своего упражнения
- [ ] Тесты на изоляцию: пользователь A не видит и не меняет упражнения пользователя B

## Этап 7. Недельный план

- [ ] API: `GET /workouts?from&to`, `POST`/`PATCH`/`DELETE`, `GET /:id`
- [ ] Фронт: стор выбранной недели, расчёт пн–вс, переключение недель, `DayHeader`, `WorkoutCard`, добавление тренировки на день
- [ ] Query keys через `workoutKeys.week(from, to)`, инвалидация после мутаций

## Этап 8. Редактор тренировки и подходы

- [ ] `shared`: схема дерева «упражнения → подходы» для `PUT`
- [ ] API: `PUT /workouts/:id/exercises` в транзакции: удалить старое и вставить новое. Транзакция нужна, чтобы при ошибке посередине тренировка не осталась наполовину пустой.
- [ ] Фронт: `ExerciseCard`, `SetRow`, `useFieldArray` в react-hook-form, выбор упражнения из каталога, порядок, вес с запятой

## Этап 9. Полировка MVP

- [ ] Пустые состояния, загрузка, ошибки, тосты
- [ ] Доступность: фокус, 44px, проверка на реальном телефоне в зале
- [ ] Дописать тесты, где их не хватает

## Этап 10. Эксплуатация

- [ ] Бэкапы: `pg_dump` по крону с ротацией и копией вне VPS. Обязательно один раз проверить восстановление из бэкапа.
- [ ] CI/CD через GitHub Actions: линт, тесты, сборка образов, деплой по SSH
